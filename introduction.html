Overview

这个 Skill 解决什么问题

外贸客户搜索最常见的失败点不是“搜不到”，而是候选公司无法核验、联系方式来源不清、同一集团重复计入、把社交讨论当成采购需求，以及后续无法复现当时的判断依据。这个 Skill 把每个环节都显式落盘。

📚平台路线

先有国家与行业入口

以 Dragon Guide 作为种子目录，沉淀各国黄页、B2B 平台、商会协会、本地搜索引擎、政府贸易与海关贸易入口，避免每次从零开始。

👤2026-08-31

关键联系人分层

支持 LinkedIn 公开页、公开档案与官方来源导入；先验证公司身份，再按域名 / LinkedIn 公司页 / 官方来源匹配关键人。

🔍已接入

再接搜索引擎扩展

支持 Google/通用搜索结果与 AnySearch 作为发现层，用多语言关键词补足目录盲区；搜索摘要只作为线索，不作为事实。

🛡️核心原则

官网核验优先

公司身份、业务范围、客户类型、公开电话和邮箱，优先打开官网或官方集团页核验；必要时用_registry、协会、商会等交叉验证。

🧾可审计

输出证据链

每条记录保留来源、核验 URL、观察日期、置信度、缺失状态和备注。谁用了什么来源、为什么保留，都能追溯。

Architecture

研究流水线架构

系统把“发现、核验、评分、交付、升级”分成明确阶段。前一段的输出永远是后一段的候选材料，不会直接变成最终事实。

1

需求定义

产品、国家、客户类型、数量、语言、排除项、时间窗与必填字段。

2

平台选择

从 1,750 个入口中筛选国家、大陆、类型与健康状态。

3

多语言搜索

组合产品词、客户类型、国家与本地语言关键词，记录查询日志。

4

实体核验

解析 canonical domain，打开官网与官方页面确认身份和业务。

5

联系人匹配

先验证雇主公司，再附加姓名、职务、平台 URL、观察日期与证据。

6

去重评分

按域名与规范公司名去重，再用 100 分模型评估证据与匹配度。

7

交付留档

输出 CSV、JSONL、Markdown 与覆盖率、阻断源、缺口报告。

Providers

搜索与网页能力接入

不同 provider 有不同证据角色。系统采用“最小必要组合”：能用目录发现的先发现，能用官网核验的先核验，需要批量抽取时才用 Firecrawl。

能力当前状态主要用途边界与限制
Dragon Guide 目录库已建立 发现国家黄页、B2B 平台、商会协会、本地搜索、政府与海关贸易入口。 Dragon Guide 收录只代表发现路线，不证明目标公司真实、活跃或符合客户画像。
Google / 通用搜索 可接入 补足目录盲区，定位官网、产品页、联系方式、协会、展会与新闻。 摘要和 AI 总结不能直接作为事实；需要打开页面并记录 URL。
AnySearch 已安装可用 批量搜索、垂直搜索、URL 提取，提高多国家、多关键词的发现效率。 返回结果仍是候选与导航线索，重要字段要回到原始页面核验。
Firecrawl Cloud 缺少 API Key search、scrape、map、crawl，用于搜索、已知页抽取、站点结构与批量页面收集。 适配器已实现，但当前未配置密钥；需要遵守 robots、访问控制、频率和服务条款。
Firecrawl Self-host 配置式支持 连接自部署 Firecrawl API，可在本地或私有环境中做受限抓取。 需要提供实际 API base；是否需要 token 取决于部署方式。
last30days 已安装可用 研究最近 30 天讨论、公司活动、需求、招聘、活动、发布等时效信号。 只做新鲜度与优先级参考，不能单独证明身份、联系方式、采购意愿或销量。
LinkedIn 公开页联系人层 公开公司页 / 个人页用于发现关键人姓名、职务与雇主证据；可用 --contacts-file 导入。 不登录、不绕过验证码或频率限制；LinkedIn API 需用户另行配置授权。公司名相似不等于匹配。
官方站 / registry 核心验证层 确认公司身份、地址、产品、业务角色、公开联系方式与组织关系。 官网自述能证明公司主张，不能自动证明其采购量、销售或未来需求。

Quality Model

验证、去重与评分

评分只用于排序，不用于把未知变成已知。缺少证据就明确标记，宁可少交付，也不填充猜测值。

评分维度分值需要什么证据
公司身份0–20canonical domain、名称一致、地点、registry 或可信交叉来源。
产品匹配0–30官网产品、品类、服务或项目证据与目标 offer 直接相关。
客户类型0–20明确进口商、分销商、批发商、零售商、工程商、买方或终端角色。
目标市场0–10有运营、销售区域、办公室、注册或市场覆盖证据。
可联系性0–10公开业务邮箱、电话、官方联系入口，或已通过公司匹配门的完整关键联系人；不推断私人邮箱。
新鲜度0–10近期官方更新或正确匹配的 last30days 信号。

置信带

  • High / 80–100：身份已验证、产品直接相关、客户类型有证据、来源强。
  • Medium / 60–79：可识别且相关，但至少一个关键字段还需要更强证据。
  • Low / <60：仅适合探索层，不进入默认合格客户集，除非用户明确要求。

缺失值规则

  • 已验证：有直接、可信来源支撑字段。
  • 待验证：有候选值但证据不足、含糊或冲突。
  • 公开渠道未找到：合理公开搜索后仍未找到，不编造。

去重主键

以 canonical domain + 规范化公司名为主，检查法律名、交易名、本地语言名、地址、国家、父子公司与品牌关系。不能只因为名字相似、地址相近或目录重复列出就合并。

集团处理

同一集团下多个品牌不重复占位；确属同一经营实体时记录别名与合并理由，仍保留原始证据。组织关系不清楚时宁可保持独立。

证据分层

目录证据、搜索证据、官网证据、联系方式证据、关键联系人证据、last30days 信号分开保存。社交或新闻热度不能替代官网身份核验。

联系人匹配门

关键人必须通过 canonical domain、公开 LinkedIn 公司页或官方来源之一匹配，且姓名、相关职务、来源 URL、观察日期与证据齐全。相似公司名、同城或搜索摘要不匹配。

不奖励猜测

未知联系人、销量、排名、采购量、私人邮箱和推断电话均为 0 分；LinkedIn 职务也不能推断采购权限、采购意愿或营销同意。

Compliance

合规与授权边界

这个 Skill 默认授权的是公开研究与本地 artifact 创建，不默认授权营销触达或任何外部写入动作。

默认允许

  • 搜索公开网页与公开商业目录。
  • 记录公司级 B2B 资格信息与公开业务联系渠道。
  • 生成 CSV、JSONL、Markdown、证据文件与覆盖率报告。
  • 明确标记缺失、冲突、过时或不确定的信息。

默认不授权

  • 发送邮件、消息、好友申请或提交表单。
  • 导入 CRM、广告受众、数据增强平台或营销系统。
  • 登录 LinkedIn 或任何平台、绕过 CAPTCHA、规避频率限制或访问控制。
  • 购买受限数据、接受新商业条款或抓取受保护数据库。
  • 推断私人邮箱、私人电话、身份、敏感属性或营销同意状态。
触达必须二次授权：如果后续要发送邮件或导入营销系统，必须另行确认适用法域、 lawful basis、 suppression list、同意要求、发件身份与渠道规则。研究完成不等于 outreach 已获授权，也不等于联系人可营销。

命令边界

doctor.py 会修改配置吗？

不会。它只报告可用性与缺失项，不写入配置，也不打印密钥。

check_upstreams.py 会自动升级吗？

不会。它只读取 GitHub 最新 release 元数据，比较版本并输出 JSON；不会下载、安装、执行或覆盖本地文件。

sync_source_catalog.py 会直接覆盖目录吗？

默认 apply 模式会写入 Skill 根目录下的 source registry 与 health 文件，因此应先用 --dry-run 和 --max-pages、--max-depth 控制范围。也可以用 --output 写到隔离目录。

dry-run 能证明搜索成功吗？

不能。dry-run 只显示查询与 provider 选择，且 network_calls: false、writes: false；它不证明 provider 会返回足够结果。

Iteration

在线升级与迭代机制

升级被拆成“目录数据刷新”和“上游代码版本检查”两条线。两者都要求显式授权与测试，不做自动覆盖，避免一次上游变化破坏可用工作流。

  1. 每次运行前

    环境诊断

    确认 AnySearch、Firecrawl、last30days、seed 导入是否可用；缺失项作为覆盖率限制记录。

  2. 数据层

    目录增量刷新

    重新访问 Dragon Guide 分类页，提取并归一化外部入口，保留历史记录，标记重定向、登录、阻断或失效。

  3. 代码层

    上游 release 检查

    只读比较 Firecrawl 与 last30days 最新 release；版本差异仅触发评审，不自动安装。

  4. 验证层

    回归测试

    运行当前 37 个单元测试，重点覆盖目录抽取、URL 归一化、provider 安全、评分、导出、信号导入与联系人匹配。

  5. 交付层

    变更报告

    说明新增、重定向、移除、兼容性、阻断源与回滚方案，再决定是否采用新版本。

FAQ

常见问题

它能保证每条客户都是真实买家吗？

不能绝对保证。它能把候选公司推进到“可验证、可审计、高置信”的层级，但采购关系、采购量和未来意愿必须有对应证据。没有证据时会标记待验证或公开渠道未找到。

为什么 Firecrawl 显示已接入但不可用？

第一版已经实现 Firecrawl Cloud 与 self-host 的配置路由和相关测试；当前本机缺少 FIRECRAWL_API_KEY，所以官方云 endpoint 无法调用。配置密钥后即可重新运行 doctor 验证。

last30days 会被复制进这个 Skill 吗？

不会。它作为独立 Skill 被调用，输出保存为 dated signals artifact，再由本 Skill 用 --signals-file 导入。这样保留原技能边界，也避免复制其内部长契约。

为什么不用更高数量填满结果？

本 Skill 的交付标准是证据质量优先。数量不足时报告缺口和阻断源，比用低置信、重复或编造记录填满 20 条更有价值。

生成联系人后可以直接群发吗？

不可以。默认授权止于研究与本地文件交付。邮件、表单、CRM 导入、广告受众或任何外部写入都需要单独授权和合规检查。

为什么 LinkedIn 匹配后仍不能直接群发？

LinkedIn 只能证明公开可见的姓名、职务和雇主线索，不证明采购权限、采购意愿、邮箱可达性或营销同意。触达前仍需单独授权、适用法域检查、lawful basis、suppression list 与渠道规则审查。

找不到关键联系人怎么办？

输出会明确标记「公开渠道未找到」，并保留 LinkedIn 登录墙、反爬或证据不足等阻断原因。可以用官方高管页、年报、新闻稿、协会名录、展会名录等替代公开来源，但不会用通用邮箱冒充关键人。

LinkedIn 出现登录墙或反爬怎么办？
